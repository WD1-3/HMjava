# 黑马点评能力矩阵

> 不再用“这一章看完了没有”衡量学习进度。
>
> 每个模块记录两个等级：
>
> - `P`：Principle，原理理解等级
> - `C`：Coding，从识别代码到从零手搓的实现等级

## 等级速查

### 原理 P0-P4

| 等级 | 标准 |
| --- | --- |
| P0 | 听过名词，知道大概用途 |
| P1 | 知道它解决什么业务问题 |
| P2 | 能不看代码讲清完整机制 / 数据流 |
| P3 | 能解释设计取舍、边界情况和常见坑 |
| P4 | 换一个业务场景也能自己设计方案 |

### 实现 C0-C5

| 等级 | 标准 |
| --- | --- |
| C0 | 看到代码能认出它在做什么 |
| C1 | 高频写法已经熟悉，有代码语感 |
| C2 | 能遮住关键代码自行补全 |
| C3 | 只给类 / 方法骨架，可以独立写主要实现 |
| C4 | 只给业务需求，可以从零设计并实现整个模块 |
| C5 | 换一个项目 / 业务背景仍能重新实现 |

# 升级规则

## P 等级怎么升级

不能因为“看懂了”就升级。

### P1 验收

不看资料回答：

> 这个功能到底解决什么问题？没有它会怎样？

### P2 验收

白纸画出完整数据流 / 调用链。

### P3 验收

回答至少 3 个：

- 为什么这样设计？
- 有什么坑？
- 有什么替代方案？
- 数据丢失 / 过期 / 并发时会怎样？

### P4 验收

换一个新业务，只给需求，自己设计一版方案。

---

# C 等级怎么升级

## C0 → C1

同一类写法反复出现后，可以快速识别，不再逐字符理解。

## C1 → C2

开始“遮代码”：

```text
保留注释 / 方法签名
→ 删除关键实现
→ 自己补
```

## C2 → C3

只保留：

```text
类名
方法名
输入输出
```

自己组织实现步骤。

## C3 → C4

删除骨架，只给业务需求。

例如：

> 实现 Redis token 登录系统。

从空白决定 Controller、Service、DTO、Redis Key、拦截器等结构。

## C4 → C5

换业务背景重新实现。
